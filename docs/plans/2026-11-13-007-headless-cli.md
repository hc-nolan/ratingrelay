# RR-3 — headless mode: a CLI over the same engine

Status: implementing
Branch: `v3`

## The ticket

> `ratingrelay` CLI that runs a relay with no server and no browser:
> `--source plex --target lastfm [--dry-run]`, relay definitions from a config file
> for unattended/cron use.
>
> - Consumes exactly the same `engine/` code path as the web app — no second copy of
>   sync logic.
> - Human summary plus a machine-readable report (JSON), exit codes that distinguish
>   success / partial failure / total failure.
> - Works with credentials from the settings file or the database; must not require
>   the API to be running.
>
> Open: ship as CLI only, or also a Docker image; and whether the API should be
> optional at install time.

## Decisions taken here

- **CLI only.** No Docker image. The repo's deploy story is `just` on a host; an image
  would double the surface (volumes, health, the frontend bundle) for no user. If
  someone wants one later it is `uv run ratingrelay run` in a thin base image, and
  nothing in this design blocks it.
- **The API is optional at install time, and already was.** Nothing in `engine/`
  imports FastAPI; the CLI imports `engine/` + `db/` + `core/` (credentials, service
  construction). It opens the SQLite file directly. `frontend/` is never touched, so
  `uv sync` + `uv run ratingrelay ...` works on a box with no web app built.
- **Cron is the target use case, so the CLI is quiet by default and loud on failure:**
  one block of human summary, per-track lines only under `--verbose`, JSON on
  `--json`, and exit codes that a shell can branch on.
- **No new dependencies.** `argparse` for flags, `tomllib` (stdlib, 3.11+) for the
  config file, `json` for the report.
- **The credentials ladder is untouched:** settings first, then the stored row. The
  CLI reads exactly what the API reads, so `./.config` and a `DATABASE` override are
  all a cron box needs.

## Exit codes

| code | meaning | test |
| --- | --- | --- |
| 0 | ran, nothing failed | `report.status == "completed"` |
| 1 | ran, some tracks failed on a target | `report.status == "partial"` |
| 2 | could not complete: no target wrote anything, or a fatal error before/while running | `report.status == "failed"` or an exception |

Unmatched tracks are *not* failures: a track Plex rates that Last.fm does not have is
the normal case, it is reported (count + details), and it does not page anyone at 3am.
A dry run can only ever exit 0 or 2 — nothing is written, so nothing can fail to be
written.

## Shape

```
ratingrelay/cli/
  __init__.py     docstring only
  __main__.py     python -m ratingrelay.cli
  main.py         argparse, exit codes, printing
  config.py       RelaySpec + relays.toml loading
  report.py       human summary and the JSON document
```

`ratingrelay/__main__.py` makes `python -m ratingrelay` work as well.

Layering: `cli/` may import `engine/`, `db/`, `core/` (credentials, service
construction) and stdlib. It may **not** import `fastapi`, `starlette`,
`ratingrelay.routes`, or `ratingrelay.schemas` — enforced by the same AST test that
guards `engine/`. A request-config pydantic model in the CLI would mean the headless
path depends on the web path's wire format.

## One copy of the wiring

`core/adapters.py` currently turns a *request config* into a source or target. The CLI
has no request configs, so the construction moves one level down into
`core/factory.py`:

```python
async def source_for_service(db, service, *, rating_threshold, comparison, feedback_type) -> Source
async def target_for_service(db, service, *, plex_rating, feedback_type) -> Target
```

`adapters.source_for` / `target_for` keep their pydantic dispatch and delegate. That
way "client from credentials, plus the mappings store and the MBID cache" exists once,
and the CLI cannot drift from the API on which store or which cache a target gets —
the thing that would silently break reconcile.

## Config file

`relays.toml`, one table per relay, loaded with `tomllib`:

```toml
[[relay]]
name = "nightly"
source = "plex"
targets = ["lastfm", "listenbrainz"]
dry_run = false
rating_threshold = 8.0     # plex source
comparison = "gte"         # plex source: gte | lte
feedback_type = "love"     # lastfm/listenbrainz
plex_rating = 10.0         # plex target
```

Unknown keys are an error (a typo in a cron file must not silently do nothing), a
missing `name` defaults to `default`, and one `[[relay]]` is as valid as ten. The file
is not a second settings system: it names *which* service talks to *which*, and every
secret still comes from settings/the credential row.

## Commands

```
ratingrelay relay --source plex --target lastfm [--target listenbrainz] [--dry-run] [--json] [--verbose]
ratingrelay run [--config relays.toml] [--only NAME] [--dry-run] [--json] [--verbose]
ratingrelay list [--config relays.toml]
```

`run` executes every relay in the file (sequentially: two relays hitting the same
service in parallel would fight over the same sync records), and exits with the worst
code of the batch.

## Report

JSON (one object per relay, one document per invocation, `null`-free):

```json
{
  "relay": "nightly",
  "source": "plex",
  "dry_run": false,
  "status": "partial",
  "tracks_fetched": 361,
  "duration_seconds": 141.2,
  "targets": [
    {"target": "lastfm", "written": 13, "reverted": 0, "skipped": 340, "unmatched": 8, "failed": 0}
  ],
  "unmatched": [{"artist": "…", "title": "…", "target": "lastfm", "reason": "no_match"}],
  "failed": []
}
```

`unmatched`/`failed` are capped (200 entries) with `truncated: true` when they hit the
cap: a JSON report that is 20 MB because the library moved is not machine-readable in
practice.

## Testing

`tests/test_cli.py`, all against fake service clients (AGENTS.md: tests never touch a
real account):

- flag parsing, repeated `--target`, unknown service rejected
- `relays.toml`: happy path, unknown key, duplicate name, missing file
- `run_relay` with an injected source/targets → exit 0 / 1 / 2, JSON shape, human
  summary text, dry run flag passed straight through to the pipeline
- an `.toml`-driven run and the same run via flags produce the same report
- `cli/` imports no framework, no routes, no schemas (AST guard)

## Not in scope

- The `reset` command. The engine exposes no reset entry point (`core/relay.py` has the
  two resets, and they are API-shaped); giving a cron job an undo-the-library button is
  a separate decision, not a free rider on headless mode.
- A daemon (`ratingrelay serve --schedule`). Cron is the scheduler; the repo already
  has the recurring-job machinery for anyone who wants it in the app.

## What landed

- **`ratingrelay/core/factory.py`** — `SOURCE_SERVICES`, `TARGET_SERVICES`, `stores()`,
  `mbid_cache()`, `source_for_service()`, `target_for_service()`. Service construction now
  exists once; `core/adapters.py` keeps its pydantic dispatch and delegates here.
- **`ratingrelay/cli/config.py`** — `RelaySpec` (a frozen dataclass that validates itself,
  so a bad flag and a bad TOML cell fail identically), `ConfigError`, `load_relays()`.
  Unknown keys, duplicate names, a missing `[[relay]]` and bad TOML are all errors.
- **`ratingrelay/cli/report.py`** — `document()` (JSON, `MAX_DETAILS = 200` with a
  `truncated` flag), `human()` (the cron-mail block), `Printer` (per-track lines).
  Every count comes from the report's own `TargetReport`; nothing recounts outcomes, so
  the CLI cannot disagree with the web app about what happened.
- **`ratingrelay/cli/main.py`** — `relay`/`run`/`list`, `--source`, repeated `--target`,
  the Plex tuning flags, `--dry-run`, `--json`, `--verbose`, `--only`, `--config`.
  `main(argv)` returns the exit code, so tests assert codes without spawning a process;
  `entry()` raises `SystemExit` for the console script.
- **Entry points** — `python -m ratingrelay`, `python -m ratingrelay.cli`, and a real
  console script (`[project.scripts] ratingrelay = "ratingrelay.cli.main:entry"`). The
  script needed the project to be installable, so `pyproject.toml` gained a hatchling
  build-system and `packages = ["ratingrelay"]`; `uv sync` now installs the package
  editable and `uv run ratingrelay …` works.
- **Docs and tooling** — README "Headless" section (usage, exit-code table, cron line),
  `relays.toml.example`, `relays.toml` gitignored, `AGENTS.md` layout/conventions, and
  `just relay`, `just relays`, `just relay-check`. Pylint `fail-under` ratcheted 9.0 → 9.7.
- **`tests/test_cli.py`** — 29 tests: flags, config-file errors, exit 0/1/2, the JSON
  document, per-target counts, dry run writing nothing, `list`, `--only`, and the AST
  guard that keeps `cli/` off FastAPI, the routes and the schemas.

### Verified live (dry runs only — nothing was written)

```
$ uv run ratingrelay relay --source plex --target lastfm --dry-run
relay default: plex → lastfm
dry run — nothing was written
fetched 361 tracks in 0.5s
  lastfm  written 13  reverted 0  skipped 352  unmatched 0  failed 0
result: completed (0 unmatched, 0 failed)
```

Those are the same numbers the last real `plex → lastfm` run produced (13 written, 352
already in sync), which is the dry-run promise: the CLI's counts are what a real run
would act on. `--json` emits one document with the same counts; no API process was
running for either.

The one thing the CLI does *not* share with the app is the job queue — a headless run
is a run, not a `job` row, so it never appears in the app's history. That is deliberate:
cron is the record, and inventing job rows for runs the worker never supervised would
put untracked work in a table the UI treats as authoritative.

### Second live dry run: the slow target

```
$ uv run ratingrelay relay --source plex --target listenbrainz --dry-run
fetched 361 tracks
  listenbrainz  written 359  reverted 0  skipped 0  unmatched 2  failed 0
result: completed (2 unmatched, 0 failed) in 635.0s
```

Two things worth keeping:

- 635 s is the honest cost of ListenBrainz *as a target*: one listen lookup per track (361
  of them), plus the cold MusicBrainz resolution. Last.fm answers in under a second
  because a plan there needs nothing but the sync record. So the CLI is not slow — the
  target is — and a cron entry that relays to ListenBrainz should not be on a 5-minute
  schedule.
- `unmatched 2` is the same pair the v3 fixes left behind, and the run still exits 0.
  That is the intended reading: two tracks Last.fm knows and ListenBrainz does not are
  the normal case, not a failure.

The first version of the human block said `fetched 361 tracks in 635.0s`, which read as
a fetch time when it was the whole run. The duration moved to the result line.
